# デイリーバトル（2026-11-03更新）

## 最新仕様

日本時間の18:30にその対戦を決着し、同じトランザクションで次回（翌日18:30決着分）の専用NPC2体を作って受付を開始する。対戦IDの日付は決着日。既存hourlyBattleの毎分トリガーを使うため、公開はその時刻以降の最初の実行となる。投票はFirestoreサーバー時刻で「前日18:30以上・決着日18:30未満」のみ。0:30の処理はない。GAS遅延時は「結果を確認中」、次回未作成時は「準備中」。未決着だった最後の対戦は復旧後に先に決着し、停止中の未作成の日をまとめて作らない。

通常のemojins/battles/legends/meta/gameのデータ・成績は変更しない。HPは抽選せず8固定。通常NPCと同じ基本スキルの重みで5枠を抽選し、6枠目はattack1。特殊スキルなし。名前は通常NPC同様のカナ3文字＋ン。通常エンジンの最大10ターン方式を使い、保存済みイベントだけを再生する。

1対戦・本人UIDごとに無料で1票、変更・取消不可。左右ともに右側の勝利/圧勝ボタンには💪を付ける指定。左から「左💪 圧勝300」「左 勝利100」「🌀 引き分け300」「右💪 勝利100」「右💪 圧勝300」。通常勝利2ボタンを広めにする。圧勝は相手HP0、通常勝利は10ターン後の残りHP差。相打ち・同HPは引き分け。

通常はスキルの左3枠だけ公開し、右3枠は?。投票候補のポップアップは別の投票ボタンへ切り替え可能で、内部の「投票」で初めて確定。確定後は全候補無効、選んでいない4つをグレーにする。別端末でも同じ投票結果を返す。

再生時は左3枠公開・右3枠?の状態から右3枠を順に派手に公開。再生は保存速度を無視して1×、スキップなし。終了後は元の通常バトル速度へ戻す。☆・💀は表示しない。当選者は再生終了後の「賞金を受け取る」を押して初めてウォレットへ加算。自然回復・3,000超の残高維持・不変receiptとトランザクションによる二重受領防止を使う。

## 開いたときの進行（未処理は最大1件）

DBの本人の最新投票を1件だけ読む。最新の実施済み対戦ではなく「本人が最後に投票した対戦」が未処理なら必ず優先する。数日不在でも飛ばさない。まだ決着前ならその投票済み対戦のカウントダウンを表示する。決着済みなら1×・スキップなしで自動再生する。

的中時は再生後の賞金受け取り画面を表示する。この段階は閉じる/次へ/別の投票の経路を作らず、「賞金を受け取る」の保存成功後に受付中の投票画面へ自動で移る。通信エラーでは受領ボタンから再試行し、未処理のまま次へ進めない。不的中時は再生完了をDBへ保存してから自動で次へ移る。保存失敗時は専用の再試行画面から完了させる。

投票文書の未処理/処理済みはDBルールで管理する。的中時の処理済み更新はwallet・不変receiptと同一トランザクションで行う。新しい投票で文書を上書きできるのは前回処理済みかつ新しい対戦日の場合だけ。同じ対戦への再投票・未受領を飛ばす書き込みも拒否する。

履歴一覧・履歴ボタン・赤丸バッジ・端末の再生済み保存は削除する。再読み込みや別端末でもDBの未処理1件へ戻る。ブラウザーを閉じた場合などの再生途中状態は保存せず、再度最初から再生する。過去の共通対戦記録と賞金receiptは、不在ユーザーの結果確認と再送の二重受領防止に必要なため残す。

## 保存場所・権限

- `dailyBattleSecrets/YYYY-MM-DD`：GASのみ。全6枠・seed。クライアントのread/writeを拒否。
- `dailyBattles/YYYY-MM-DD`：認証済みread、GASのみwrite。決着前は名前・絵文字・HP・左3枠だけ。決着後だけlog/outcomeを追加。
- `meta/dailyBattle`：GASのみwrite。通常のmeta/gameを使わない。
- `dailyBattlePlayers/{uid}`：本人のみread/writeする最新投票1件。day/choice/votedAt/settled/settledAt/uid。投票先は0〜4。初回は受付中だけcreate、前回処理済みなら次回投票で上書き。未処理→処理済みは公開済み結果と必要な賞金receiptで照合。votedAt/settledAtはserverTimestamp。削除・投票先変更・未処理のままの次回投票は拒否。
- `wallets/{uid}/operations/daily-battle-YYYY-MM-DD`：不変の賞金receipt。的中済みの最新投票・公開結果・賞金額・同時ウォレット更新のrevision/残高増分/recentOperationsと、最新投票の処理済みへの同時更新をルールで照合。通常のwallet/スロット/くじの保存経路は維持。

同時受領では片方の古いwallet revisionをルールが先に拒否する場合がある。その場合でも、すでに確定済みの同じ日付のreceiptと最新財布が取得できたときだけ成功扱いで同じ記録を返す。receiptがなければ権限エラーを握りつぶさない。

## ソースと確認

純粋な日次エンジンはapp.jsのDaily Battle区間が正本。`node scripts/sync-daily-battle.cjs`で`gas/DailyBattleEngine.gs`へ同期し、`--check`で一致を確認する。通常エンジンの同期とは別。スケジューラーは`gas/DailyBattleScheduler.gs`。Code.gsは既存hourlyBattleへ呼び出し1か所を追加するだけで、毎分トリガーは維持。日次処理の失敗はログに記録して次の毎分で再試行し、通常の定期処理を妨げない。

```sh
node --check app.js
node --check sw.js
node scripts/sync-gas-engine.cjs --check
node scripts/sync-daily-battle.cjs --check
node --test tests/*.test.cjs
python3 tests/daily-battle.py
python3 tests/replay-v4.py
python3 tests/pwa-v4.py
```

ローカルのFirestore Emulatorはfirebase.test.jsonとdemo-emojin-v4だけを使う。テスト用Firebaseプロジェクトの準備は不要。本番へテスト投票・賞金・サンプル対戦を書き込まない。

3. ファイル一式を保存する。既存hourlyBattleの毎分トリガーはそのままでよく、追加トリガーやWebアプリのデプロイは不要。次の毎分トリガーから処理が始まる。
4. Firestoreルール全文を同梱のfirestore.rulesへ更新・公開する。通常ゲームのメンテナンスやトリガー停止は不要。新規コレクションを管理画面で手作成する必要もない。
5. 次の毎分処理後、GASで読み取り専用`checkDailyBattle`を手動実行する。dayが次に迎える18:30の日付（18:30以降は翌日）、exists:true、status:open、publicSlotCounts:[3,3]、closeAtJSTがその日の18:30となることを確認する。not-createdならhourlyBattleの実行履歴を確認する。ログに非公開スキルやseedは出さない。
6. ユーザーがGAS保存・ルール公開・上記確認の完了を知らせた後、検証済みフロントをmainへ反映する。GitHub Pagesの配信内容を照合する。PWAのプレイ中/保存中の安全な更新延期を維持する。
